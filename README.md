## Описание

Проект собирает материалы сайтов **Игромания**, **StopGame** и **VGTimes**, выделяет
текст страниц и строит собственный поисковый индекс. Пользователь может выполнять
булевы запросы или искать по свободному тексту с ранжированием TF-IDF.

Поисковый робот и извлечение корпуса написаны на Python. Токенизация,
лемматизация, анализ закона Ципфа, построение индекса и поиск реализованы на C++17.
Исходные страницы и промежуточные результаты хранятся в MongoDB. Готовый индекс
представляет собой каталог файлов: для поиска подключение к базе не требуется.

Управление выполняется через терминал. Веб-интерфейс и HTTP API в проекте не реализованы.

## Как работает

1. Робот читает `robots.txt` и карты сайта, формирует постоянную очередь URL.
2. HTML-страницы сохраняются в MongoDB вместе с адресами, хешами и HTTP-метаданными.
3. Модуль `corpus` выделяет заголовок, основной текст и метаданные страниц.
4. Токенизатор разбивает текст на нормализованные токены с позициями и байтовыми границами.
5. Лемматизатор получает словарные формы русских слов и сохраняет варианты разбора.
6. По завершённой лемматизации строится сжатый инвертированный индекс.
7. Пользователь выполняет булев поиск или получает выдачу, отсортированную по TF-IDF.

```text
Игромания / StopGame / VGTimes
              │
           crawler
              │
       HTML в MongoDB
              │
            corpus
              │
          tokenizer
              │
         lemmatizer ──────────► zipf: частоты, график и отчёт
              │
        boolean-index
              │
      Сжатый файловый индекс
              │
        boolean-search
        ├── булев поиск
        └── ранжирование TF-IDF
```

## Функционал

| Модуль | Возможности |
| --- | --- |
| `crawler` | Обход sitemap и вложенных gzip-карт, учёт robots.txt, ограничение домена, параллельные запросы, квоты источников, повторные попытки и продолжение после остановки |
| Повторный обход | Условные запросы ETag/Last-Modified, обработка 304, сравнение SHA-256, обновление изменившихся страниц, планирование следующей проверки |
| `corpus` | Диагностическая выборка и извлечение корпуса, удаление HTML-шума, метаданные, статистика размеров, примеры HTML/TXT и Markdown-отчёт |
| `tokenizer` | Unicode-токенизация, нижний регистр и NFC, позиции и UTF-8-границы, статистика, разбиение записей на части |
| `lemmatizer` | Словарный анализ XMorphy, все кандидаты леммы, ограниченный LRU-кеш, checkpoint и возобновление обработки |
| `zipf` | Частотный словарь основной леммы, сравнение с законом Ципфа, оценка наклона, PNG-график, CSV и отчёт |
| `boolean-index` | Внешняя сортировка и многоуровневое слияние, частоты по полям, сжатие postings, нормы TF-IDF, контрольные суммы и атомарная публикация |
| `boolean-search` | `AND`, `OR`, `NOT`, скобки, свободный текст с TF-IDF, интерактивный режим, JSON, пагинация и проверка целостности |
| `tests` | Общий запуск Python- и C++-тестов, разделы по модулям, юнит-тесты и отдельные проверки MongoDB, словарей и CLI |

## Требования

### Для запуска через Docker

- Docker Engine или Docker Desktop с Linux-контейнерами.
- Docker Compose v2, команда `docker compose`.
- Интернет для сборки образов и обхода сайтов.
- Место для MongoDB, промежуточных данных, отчётов и индексов.

### Для запуска без Docker

| Компонент | Требование |
| --- | --- |
| ОС | Linux; для Windows используйте WSL2 или Docker с Linux-контейнерами |
| Python | 3.11 или новее |
| MongoDB | В Compose используется 8.0; для воспроизводимого локального запуска используйте ту же версию |
| C++ | Компилятор с поддержкой C++17 |
| CMake | 3.24 или новее |
| Библиотеки | ICU 67+, OpenSSL, Cairo, Boost headers, MongoDB C++ Driver |
| Служебные инструменты | Git, pkg-config, make или другой генератор CMake |

Файловый индекс использует Linux `renameat2(RENAME_NOREPLACE)` и `fsync`.
Нативный запуск всего проекта на Windows/macOS без адаптации этого участка не предусмотрен.

CMake при необходимости загружает MongoDB C Driver 1.29.2, MongoDB C++ Driver 3.11.0
и закреплённую ревизию XMorphy. Если системные заголовки Boost не найдены,
загружается Boost 1.85.0. Первый запуск сборки может потребовать заметного времени.

## Настройка

Все команды ниже выполняются из корня проекта. Файл [config.yaml](config.yaml)
уже входит в репозиторий; создавать его из отсутствующего шаблона не требуется.

Для первого знакомства установите `logic.target_documents: 1000`.
В текущем конфигурационном файле задана цель **1 000 000 документов**.

### Подключение к MongoDB

Для контейнеров оставьте в `config.yaml`:

```yaml
db:
  uri: mongodb://mongo:27017
  database: crawler
```

Для локальных Python-команд создайте отдельную конфигурацию:

```bash
cp config.yaml config.local.yaml
```

В `config.local.yaml` замените URI на `mongodb://127.0.0.1:27017`.
Остальные параметры можно оставить такими же. Имя `mongo` доступно внутри сети
Compose; локальные приложения обращаются к `127.0.0.1`.

### Параметры робота

| Параметр `logic` | Назначение |
| --- | --- |
| `target_documents` | Общее целевое число собранных документов |
| `recrawl_interval_days` | Интервал успешных повторных проверок |
| `request_timeout_seconds` | Таймаут HTTP-запроса |
| `max_retries` | Максимум попыток первичной задачи |
| `retry_base_seconds` | Основа экспоненциальной задержки повторов |
| `lease_seconds` | Время захвата задач и блокировки робота |
| `max_html_bytes` | Лимит HTML; не более 8 000 000 байт |
| `max_sitemap_bytes` | Лимит sitemap, включая размер после распаковки |
| `poll_seconds` | Пауза при отсутствии доступной работы |
| `user_agent` | Идентификатор HTTP-клиента |

В `sources` задаются `name`, точный `domain`, список `sitemap_urls`,
`delay_seconds` и `concurrency`. Имена и домены должны быть уникальными.
Адреса HTML-ссылок на страницах не обходятся: источником URL служат sitemap.
Настройки robots.txt могут увеличить задержку относительно YAML.

### Переменные окружения

Обязательного `.env` с токенами нет. Compose может читать следующие значения
из окружения или локального `.env`:

| Переменная | Назначение |
| --- | --- |
| `MONGODB_URI` | URI для C++-приложений; Compose задаёт контейнерный адрес автоматически |
| `BOOLEAN_UID`, `BOOLEAN_GID` | Пользователь контейнеров индекса и поиска; по умолчанию 1000:1000 |
| `ZIPF_UID`, `ZIPF_GID` | Пользователь контейнера Zipf; по умолчанию 1000:1000 |
| `TOKENIZER_TEST_URI` | Подключение интеграционных тестов токенизатора |
| `LEMMATIZER_TEST_URI` | Подключение интеграционных тестов лемматизатора |
| `BOOLEAN_TEST_URI` | Подключение интеграционных тестов индекса |

Python-crawler читает URI из YAML. Для `corpus` также доступен аргумент `--uri`.

## Запуск через Docker

Команды рассчитаны на Bash в Linux или WSL2. В Windows/macOS установите Docker
Desktop и используйте Linux-контейнеры; для приведённых команд удобнее Linux-оболочка.
Перед запуском проверьте доступность `docker` и `docker compose`.

### 1. Подготовка каталогов и сборка

```bash
mkdir -p docx/runs indexes
export BOOLEAN_UID="$(id -u)"
export BOOLEAN_GID="$(id -g)"
export ZIPF_UID="$(id -u)"
export ZIPF_GID="$(id -g)"

docker compose build crawler tokenizer lemmatizer zipf boolean-index
```

`boolean-index` и `boolean-search` используют один образ `web-search-boolean`.
В C++-образах Dockerfile выполняет предусмотренные для образа CTest-проверки
во время сборки. Общая команда всех тестов проекта описана отдельно ниже.

### 2. Сбор страниц

```bash
docker compose up -d mongo crawler
docker compose logs -f crawler
```

Робот сначала собирает целевое число уникальных документов, затем остаётся
работать в режиме повторных проверок. Достижение цели не означает завершение процесса.
Для проверки количества документов откройте другой терминал:

```bash
docker compose exec mongo mongosh crawler --quiet --eval 'db.documents.countDocuments({})'
```

### 3. Извлечение корпуса

Пока робот работает, можно получить диагностическую выборку:

```bash
docker compose run --rm --user "$(id -u):$(id -g)" corpus \
  inspect /app/config.yaml --run-id inspect-demo --limit 30 --output /app/docx/runs
```

Для полного извлечения остановите робот. `extract` захватывает его блокировку
на время прохода, чтобы исходный набор не менялся:

```bash
docker compose stop crawler

docker compose run --rm --user "$(id -u):$(id -g)" corpus \
  extract /app/config.yaml --run-id corpus-demo --output /app/docx/runs
```

После аварийной остановки может потребоваться дождаться истечения `lease_seconds`.
При штатной остановке робот освобождает блокировку. После завершения `extract`
его можно снова запустить через `docker compose start crawler`.

### 4. Токенизация и лемматизация

```bash
docker compose run --rm --user "$(id -u):$(id -g)" tokenizer \
  --corpus-run corpus-demo --run-id tokens-demo --output /app/docx/runs

docker compose run --rm --user "$(id -u):$(id -g)" lemmatizer \
  --tokenization-run tokens-demo --run-id lemmas-demo --output /app/docx/runs
```

В контейнере XMorphy-словари установлены автоматически.

### 5. Анализ закона Ципфа

```bash
docker compose run --rm zipf --lemmatization-run lemmas-demo
```

Результаты появятся в `docx/runs/zipf-lemmas-demo/`. Этот этап нужен для анализа
корпуса, но не является обязательным условием построения поискового индекса.

### 6. Построение индекса

```bash
docker compose run --rm boolean-index \
  --lemmatization-run lemmas-demo \
  --output /app/indexes/games-demo \
  --memory-budget-mib 256
```

### 7. Поиск и проверка

```bash
docker compose run --rm --no-deps boolean-search \
  --index /app/indexes/games-demo \
  --query '(игры OR обзоры) AND NOT реклама' --json

docker compose run --rm --no-deps boolean-search \
  --index /app/indexes/games-demo \
  --mode tfidf --query 'обзоры новых игр PS5' --limit 10 --json

docker compose run --rm --no-deps boolean-search \
  --index /app/indexes/games-demo --verify

docker compose run --rm --no-deps boolean-search \
  --index /app/indexes/games-demo --mode tfidf --interactive
```

Поиск не зависит от MongoDB. Каталог индекса смонтирован в поисковый контейнер
только для чтения. `--verify` также не требует словарей XMorphy.

**Повторный проход:** замените `corpus-demo`, `tokens-demo`, `lemmas-demo` и
`games-demo` новыми идентификаторами. Готовые результаты не перезаписываются.
Сервисы обработки имеют профиль `analysis` и запускаются явно через `compose run`;
обычный `docker compose up` запускает MongoDB и crawler.

## Запуск без Docker

### 1. Установка зависимостей

Пример установки инструментов для Debian 12 / совместимого Linux:

```bash
sudo apt-get update
sudo apt-get install -y python3 python3-venv python3-pip build-essential \
  cmake git ca-certificates pkg-config libicu-dev libssl-dev libboost-dev \
  libcairo2-dev libsasl2-dev

python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
```

Убедитесь, что установлены Python 3.11+ и CMake 3.24+. Если пакеты вашей ОС
содержат более старые версии, обновите их перед сборкой.

### 2. Запуск MongoDB

Установите MongoDB Community Server 8.0 средствами своей ОС. Запустите системную
службу либо отдельный `mongod` с собственным каталогом данных:

```bash
mkdir -p "$HOME/.local/share/web-search/mongo"
mongod --dbpath "$HOME/.local/share/web-search/mongo" --bind_ip 127.0.0.1 --port 27017
```

При запуске этой командой MongoDB работает в текущем терминале. Остальные
команды выполняйте в другом терминале из корня проекта, активировав `.venv`.
Если сервер уже работает на порту 27017, второй экземпляр запускать не нужно.

### 3. Сборка C++-модулей

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release \
  -DTOKENIZER_WITH_MONGO=ON \
  -DLEMMATIZER_BUILD=ON -DLEMMATIZER_WITH_MONGO=ON \
  -DZIPF_BUILD=ON \
  -DBOOLEAN_BUILD=ON -DBOOLEAN_BUILD_INDEX=ON -DBOOLEAN_BUILD_SEARCH=ON \
  -DBUILD_TESTING=ON

cmake --build build --parallel 4
```

Параметры модулей переданы явно: CMake сохраняет предыдущие значения в кеше.
Без `ZIPF_BUILD=ON` и `BOOLEAN_BUILD=ON` соответствующие модули по умолчанию отключены.

Если зависимости уже установлены локально, добавьте при конфигурации нужные пути:

```bash
cmake -S . -B build \
  -DXMORPHY_SOURCE_DIR=/path/to/XMorphy \
  -DBOOST_HEADERS_DIR=/path/to/boost \
  -DCMAKE_PREFIX_PATH=/path/to/mongo/install
```

XMorphy должен соответствовать ревизии `88eb5b84e28f0e00672f07e4fe92e88262242163`.
`BOOST_HEADERS_DIR` указывает на каталог, внутри которого находится папка `boost/`.
Настройки модулей из предыдущего вызова CMake сохранятся.

### 4. Полный цикл обработки

Подготовьте `config.local.yaml`, как описано в разделе настройки, и запустите робот:

```bash
python -m crawler config.local.yaml
```

После сбора нужного количества страниц завершите робот через `Ctrl+C`.
Затем выполните обработку:

```bash
export MONGODB_URI='mongodb://127.0.0.1:27017/?serverSelectionTimeoutMS=10000'

python -m corpus extract config.local.yaml --run-id corpus-demo

./build/tokenizer --corpus-run corpus-demo --run-id tokens-demo

./build/lemmatizer --tokenization-run tokens-demo --run-id lemmas-demo

./build/zipf --lemmatization-run lemmas-demo

./build/boolean-index --lemmatization-run lemmas-demo \
  --output indexes/games-demo --memory-budget-mib 256

./build/boolean-search --index indexes/games-demo \
  --mode tfidf --query 'обзоры новых игр PS5' --json
```

По умолчанию C++-приложения используют базу `crawler`. Модуль Zipf работает
именно с этой базой; отдельного аргумента `--database` у него нет.
Для остальных приложений обработки доступен `--database`.

Лемматизатор и поисковый CLI используют путь словарей, заданный при сборке.
При переносе бинарников укажите `--dictionary /path/to/dicts`, где находятся
`udmaindict.bin` и `udaffixdict.bin` закреплённой версии XMorphy.

## Использование модулей

### Поисковый робот

```bash
python -m crawler config.local.yaml
```

Робот допускает один экземпляр на базу. URL и очередь сохраняются в MongoDB,
поэтому перезапуск продолжает работу. Задачи аварийно завершившегося процесса
возвращаются в работу после истечения захвата.

Начальные квоты приблизительно равны между источниками. Если карты одного
источника исчерпаны, его неиспользованная квота перераспределяется. Общий лимит
учитывает уже выданные задачи. Ошибки источника не считаются его исчерпанием.

При повторном обходе 304 сохраняет предыдущий HTML, изменившийся 200 обновляет
последнюю версию, а 404/410 фиксируются без удаления сохранённого содержимого.
История версий HTML не ведётся. Ошибки повторной проверки откладываются;
при недостаточной скорости обхода очередь повторных проверок может отставать.

### Извлечение и диагностика корпуса

```bash
python -m corpus inspect config.local.yaml \
  --source stopgame --limit 30 --run-id inspect-stopgame

python -m corpus extract config.local.yaml \
  --source stopgame --source vgtimes \
  --url-pattern '/news/' --limit 1000 --run-id corpus-news
```

`inspect` читает работающую базу без записи корпуса в MongoDB; по умолчанию
берёт до 100 документов. Его выборка не является общим снимком базы.
`extract` требует остановленного crawler и сохраняет неизменяемый набор запуска.
При нескольких источниках и общем лимите применяется выборка по очереди из источников.

Модуль выделяет заголовок и основной текст, язык, автора и дату публикации;
удаляет навигацию, рекламу и другой распознаваемый шум. Для неподдержанной
разметки используется извлечение видимого текста с предупреждением.
Карточки игр и страницы подборок отмечаются отдельно.

| Параметр | Назначение |
| --- | --- |
| `--uri URI` | Переопределение URI из конфигурации |
| `--run-id ID` | Идентификатор запуска; без аргумента создаётся автоматически |
| `--source NAME` | Фильтр источника; можно повторять |
| `--url-pattern REGEX` | Фильтр URL по регулярному выражению |
| `--limit N` | Общий положительный лимит документов |
| `--batch-size N` | Размер чтения пачки, по умолчанию 100 |
| `--samples-per-source N` | Число сохраняемых примеров, минимум 2, по умолчанию 5 |
| `--output DIR` | Каталог результатов, по умолчанию `docx/runs` |

### Токенизация

```bash
./build/tokenizer --corpus-run corpus-demo --run-id tokens-demo \
  --source stopgame --limit 1000 --output docx/runs
```

Без `--corpus-run` выбирается последний завершённый корпус. Параметры
`--source` и `--limit` ограничивают набор документов. Приложение читает записи
корпуса со статусом `ok`, обрабатывает `title` и `text` и сохраняет части токенизации.

Токены включают Unicode-буквы, десятичные цифры и допустимые комбинируемые знаки.
Нормализация выполняет перевод в нижний регистр и NFC. Позиции считаются внутри
поля, а границы задаются байтовыми смещениями UTF-8. Стоп-слова и числа сохраняются.

### Лемматизация и возобновление

```bash
./build/lemmatizer --tokenization-run tokens-demo --run-id lemmas-demo \
  --batch-size 100 --cache-size 20000 --max-token-codepoints 128

./build/lemmatizer --resume lemmas-demo
```

Русские слова анализируются словарём XMorphy. Иностранные и неподдерживаемые
токены сохраняются; неизвестные русские слова не заменяются предсказаниями
по суффиксам. Основная лемма выбирается лексикографически среди кандидатов:
снятие неоднозначности по контексту не выполняется.

Без `--tokenization-run` выбирается последний завершённый запуск токенизации.
Доступны `--source`, `--limit`, `--dictionary`, `--uri`, `--database` и `--output`.
`--cache-size 0` отключает кеш; `--max-token-codepoints` допускает значения 1–4096.

`--resume` восстанавливает сохранённые настройки и продолжает незавершённый
или ошибочный запуск с checkpoint после освобождения его lease. Допустимо
переопределить только URI, базу и путь словарей. Завершённый запуск повторно
возобновить нельзя. Запуск с ошибками записей получает `completed_with_errors`;
Zipf и построитель индекса принимают только `completed`.

### Закон Ципфа

```bash
./build/zipf --lemmatization-run lemmas-demo
```

Модуль считает одну основную лемму на вхождение в поле `text`, включая все
его части. Заголовки и альтернативные кандидаты не суммируются. Стоп-слова,
числа и иностранные слова остаются в распределении.

Частоты сравниваются с `f(r) = N / (H_V · r)`. В отчёте приводятся доля единичных
терминов, ошибка в логарифмическом масштабе и оценка наклона регрессии.
График строится по логарифмическим осям. Без ID выбирается последний `completed`,
а для результатов создаётся автоматически именованный каталог.

### Построение индекса

```bash
./build/boolean-index --lemmatization-run lemmas-demo \
  --output indexes/games-demo --memory-budget-mib 256
```

Индексируется набор выбранного запуска со всеми его ограничениями. Для каждого
документа объединяются части `title` и `text`, частоты полей сохраняются отдельно.
Каждый уникальный кандидат леммы получает одно вхождение на исходный токен.

Построитель проверяет входные запуски, ссылки на записи, порядок частей,
статистику, словари и версии нормализации. Для чтения создаётся вспомогательный
индекс MongoDB, поэтому требуются права чтения и `createIndex`.

`--output` обязателен и должен указывать на новый каталог. Без ID используется
последняя завершённая лемматизация. `--memory-budget-mib` ограничивает оценочный
буфер сортировки, а не весь RSS: дополнительно расходуются память драйвера,
буферы слияния и массив норм — около 8 МБ на миллион документов.

Сегменты сливаются максимум по 16 одновременно. Перед публикацией выполняются
полная проверка, синхронизация файлов и атомарное переименование каталога.
Продолжения построения по checkpoint нет: после ошибки нужен новый запуск.

## Поисковые запросы

### Булев поиск

```bash
./build/boolean-search --index indexes/games-demo \
  --query '(игры OR обзоры) AND NOT реклама' --limit 20 --offset 0 --json
```

| Запрос | Значение |
| --- | --- |
| `игры PS5` | Оба термина: неявный `AND` |
| `игры OR PS5 AND Xbox` | `игры OR (PS5 AND Xbox)` |
| `(игры OR обзоры) NOT реклама` | Исключить документы с термином «реклама» |
| `NOT PS5` | Все документы индекса без термина PS5 |
| `стали` | Совпадение по кандидатам «сталь», «стать» или исходной нормализованной форме |

Булев режим используется по умолчанию; явно задаётся через `--mode boolean`.
Приоритет операторов: `NOT`, `AND`, `OR`. Операторы распознаются в верхнем
регистре. Выдача упорядочена по внутреннему ID документа.

### Поиск с TF-IDF

```bash
./build/boolean-search --index indexes/games-demo \
  --mode tfidf --query 'обзоры новых игр PS5' --limit 10 --json
```

В этом режиме достаточно совпадения любого термина запроса. Документы
сортируются по убыванию косинусной оценки, при точном равенстве — по ID.
JSON содержит `mode: "tfidf"` и `score` у каждого результата.

Булевы выражения в TF-IDF не разбираются: `AND`, `OR`, `NOT` становятся
поисковыми словами, а пунктуация обрабатывается токенизатором.

### Интерактивный режим и проверка

```bash
./build/boolean-search --index indexes/games-demo --mode tfidf --interactive
./build/boolean-search --index indexes/games-demo --verify
```

В интерактивном режиме вводите по одному запросу на строку. Пустые строки
пропускаются; EOF (`Ctrl+D` в Linux) завершает сеанс. Ошибка запроса не закрывает
интерактивный сеанс. `--json` выдаёт отдельный JSON-объект на каждую строку.

| Параметр | Назначение |
| --- | --- |
| `--index DIR` | Обязательный каталог индекса |
| `--query TEXT` | Один запрос |
| `--interactive` | Чтение запросов из stdin |
| `--verify` | Проверка SHA-256, структуры postings, частот и норм |
| `--mode boolean\|tfidf` | Режим поиска |
| `--limit N` | Размер страницы, по умолчанию 20, максимум 100000; 0 — только число совпадений |
| `--offset N` | Число пропускаемых результатов |
| `--json` | Машиночитаемый вывод |
| `--dictionary DIR` | Переопределение пути словарей |

Выберите ровно один из `--query`, `--interactive` и `--verify`.
`total` всегда считается по всем кандидатам; небольшой лимит не отменяет полного
обхода совпадений. Для TF-IDF `offset + limit` ограничено 100000, кроме `--limit 0`.
Нормы в интерактивном TF-IDF загружаются один раз на сеанс.

### Ограничения поиска

- Фразовый, нечёткий и wildcard-поиск, а также фильтры по отдельным полям не реализованы.
- В булевом режиме кавычки и символические операторы `&`, `|`, `!`, `*`, `?` отклоняются.
- Токенизатор разбивает `Counter-Strike` на два слова, `C++` — на `c`, `S.T.A.L.K.E.R.` — на отдельные буквы.
- Запрос ограничен 16384 байтами. Булев разбор также ограничен 256 лексическими токенами, 512 узлами/термами и глубиной 64; TF-IDF — 256 токенами и 512 расширениями.
- Неоднозначные леммы расширяют поиск; это не семантическое понимание запроса.

## Сжатие и TF-IDF

Формат индекса — **`boolean-v2`**. В postings сохраняются тройки:

```text
разность ID, частота в title, частота в text
```

Первый ID кодируется как `id + 1`, следующие — положительными разностями.
Числа записываются unsigned LEB128: по 7 полезных бит на байт, старший бит
обозначает продолжение. Декодирование выполняется потоково. Словарь и метаданные
документов сохраняются без сжатия для произвольного доступа.

Используется следующая схема весов с натуральным логарифмом:

```text
f(t,d)   = tf_title(t,d) + tf_text(t,d)
tf(t,d)  = 1 + ln(f(t,d)), если f > 0; иначе 0
idf(t)   = 1 + ln((N + 1) / (df(t) + 1))
w(t,d)   = tf(t,d) × idf(t)
norm(d)  = sqrt(Σ по всем терминам документа w(t,d)²)
score    = Σ w(t,d) × w(t,q) / (norm(d) × norm(q))
```

`N` — число документов выбранного индекса, включая пустые; `df` — число
документов с термином хотя бы в одном поле. Заголовок и текст имеют равные веса.
Повторы запроса увеличивают его TF, повторные кандидаты одного токена удаляются.
Термины вне словаря индекса исключаются из вектора запроса и его нормы.
Пустой после токенизации запрос отклоняется; полностью неизвестный возвращает ноль совпадений.

Ранжирование сливает списки по ID и сохраняет лучшие результаты в ограниченной
куче; массив оценок по всему корпусу не создаётся. Нормы занимают `8 × N` байт.
Статистика построения содержит фактический размер postings и несжатый эквивалент
тех же данных — `20 × число связей`. Старый v1 хранил только ID, поэтому сравнение
его размера с новым индексом также отражает добавление частот.

Индексы v1 не читаются: их нужно перестроить из сохранённой лемматизации.
Инкрементальное обновление индекса не реализовано; новый корпус публикуется
в новом каталоге индекса.

## Автотесты

После установки зависимостей весь набор запускается **одной командой** из корня:

```bash
python3 -m tests
```

Команда выполняет Python `unittest`, конфигурирует все C++-модули в отдельном
`build-tests/`, собирает их и запускает CTest. При ошибке Python-тестов, сборки
или CTest возвращается ненулевой код. Docker автоматически не запускается.

| Раздел | Что проверяется |
| --- | --- |
| `tests/crawler` | Конфигурация, HTTP, robots, sitemap, очередь, обход и recrawl |
| `tests/corpus` | HTML, метаданные, статистика, отчёты, snapshot и CLI |
| `tests/text` | UTF-8 и Unicode-нормализация |
| `tests/tokenizer` | Токены, границы, статистика, отчёты и MongoDB |
| `tests/lemmatizer` | Политика, кеш, словари, параметры, checkpoint и MongoDB |
| `tests/zipf` | Входные частоты, расчёты и файлы отчёта |
| `tests/boolean` | Булев поиск, сжатие, слияние, TF-IDF, целостность и MongoDB |

Python-тесты подменяют HTTP и MongoDB; реальная сеть запрещена фикстурами.
В CTest отдельно помечены `unit`, `integration`, `dictionary`, `cli` и раздел модуля.
Часть юнит-тестов требует библиотек драйвера при сборке, но не сервера MongoDB.

```bash
python3 -m tests --unit-only
python3 -m tests --section crawler
python3 -m tests --section boolean --jobs 2
```

Для нестандартных путей доступны `--build-dir PATH` и повторяемый
`--cmake-arg=-DNAME=VALUE`. Запуск только раздела Python не требует CMake.

Интеграционные тесты БД без своих URI получают статус `Skipped`, код 77.
Чтобы включить их в тот же общий запуск, предварительно запустите тестовый MongoDB:

```bash
TOKENIZER_TEST_URI='mongodb://127.0.0.1:27017/?serverSelectionTimeoutMS=3000' \
LEMMATIZER_TEST_URI='mongodb://127.0.0.1:27017/?serverSelectionTimeoutMS=3000' \
BOOLEAN_TEST_URI='mongodb://127.0.0.1:27017/?serverSelectionTimeoutMS=3000' \
python3 -m tests
```

Тесты создают уникальные базы `tokenizer_test_*`, `lemmatizer_test_*`,
`boolean_test_*` и удаляют их после работы. Используйте отдельный тестовый
сервер с правами на создание и удаление этих баз. Если URI задан, ошибка
подключения считается ошибкой теста, а не основанием для пропуска.

Успешное прохождение и процент покрытия пока не подтверждены запуском.
Юнит-тесты также не заменяют оценку релевантности и нагрузочные измерения
на полном корпусе.

## Диагностика

### Состояние робота и очереди

```bash
docker compose ps
docker compose logs --tail 100 crawler
docker compose exec mongo mongosh crawler --quiet --eval 'db.state.findOne({_id:"progress"})'
docker compose exec mongo mongosh crawler --quiet --eval 'db.crawl_queue.find({status:"failed"},{url:1,last_error:1}).limit(10).toArray()'
```

После устранения причины ошибок можно вернуть неудачные первичные задачи в очередь:

```bash
docker compose stop crawler
docker compose exec mongo mongosh crawler --quiet --eval 'db.crawl_queue.updateMany({status:"failed"},{$set:{status:"pending",attempts:0,next_attempt:0}})'
docker compose start crawler
```

Для MongoDB без Docker выполните те же JavaScript-запросы через локальный
`mongosh 'mongodb://127.0.0.1:27017/crawler'`.

### Типичные ситуации

| Ситуация | Решение |
| --- | --- |
| `extract` сообщает об активном crawler | Остановите робот; после аварии дождитесь истечения его lease |
| Из контейнера не находится MongoDB | Используйте URI `mongodb://mongo:27017`; с хоста — `127.0.0.1` |
| Нет прав записи отчётов | Создайте каталоги заранее; Python-сервисы запускайте с `--user`, для Zipf/индекса задайте UID/GID |
| `No completed run` | Проверьте порядок этапов и статус конкретного запуска в MongoDB |
| Каталог или run ID уже существует | Используйте новый идентификатор; готовые результаты не заменяются |
| Несовместимый индекс или словари | Используйте закреплённые словари и одинаковые версии нормализации; перестройте индекс |
| После аварии остался `INDEX.tmp-*` | Это незавершённые данные; не используйте их для поиска, повторите построение |
| Сборка не загружает зависимости | Проверьте сеть/DNS или передайте пути к локальным зависимостям CMake |

После изменения YAML перезапустите робот. После изменения исходников пересоберите
нужный образ или C++-цель. Точную справку по аргументам дают `python -m corpus --help`
и `--help` у каждого C++-приложения. У crawler единственный позиционный аргумент — YAML.
